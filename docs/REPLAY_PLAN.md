# Replays and resume — plan

Status: **resume in part, replays not started** (2026-10-21). Built: the command log
(`GameSession.commandLog`), `SessionReplay`, and one game in progress (`GameInProgress`, the
`gameInProgress` document): leaving a game that is not over pauses and stores it, a game the
app is hidden from is stored, and Play offers Resume (rebuilt, checked against its state hash,
opened paused) or Discard (owner request; `docs/DEVIATIONS.md` `gameInProgress`). Not built:
the pause window, auto-pause, data blobs and `simVersion` (§4; a changed app is caught by the
state hash instead and the player may resume anyway or discard), replays and their storage.
Owner decisions still open are listed in §12.

## 1. Goal

**Replays.** Let the player re-watch games they played, including after closing and
reopening the app:

- play / pause, restart from the beginning, a few preset playback speeds;
- rewind and fast-forward (jump back / forward in time);
- skip to a future wave or go back to a past wave;
- step to the previous / next player action;
- a **Recent** list of the last 10 finished games, and a separate **Saved** list for replays
  the player keeps permanently.

**Resume.** A player who leaves or closes the app never loses their place:

- the game **auto-pauses** whenever the app stops being active, and a **pause window** offers
  Resume, Restart and Main menu;
- the game in progress is saved continuously and can be **continued** after the app is
  closed, killed or restarted;
- there is **exactly one game in progress** at a time: a new game cannot start until the
  player continues or abandons the current one.

Everything the player did (build, upgrade, sell, move, target mode, lock, send wave, pause,
game speed) is an **action** on the timeline. Each action can be replayed (done again at its
tick) and undone (the timeline is taken back to just before it).

**Naming.** "Saved replays" are finished games kept to watch. "The game in progress" is the
one resumable game. They are different things and the UI must never call the game in
progress a "save" next to a list of saved replays.

## 2. Design: one action log for both

The simulation is deterministic: same `GameConfig` (seed, map, mode, difficulty, profile) +
same `GameData` + same `GameCommand`s at the same ticks ⇒ the same game, bit for bit. The
regression fixtures and `test/regression/determinism_test.dart` prove this every CI run, and a
fixture `Scenario` is already "config + `[{tick, command}]`".

So **a replay is the config, the game data, and the log of player commands with the tick each
was applied.** We replay the player's *inputs*, never the game's *outputs*: kills, hits,
waves and creep movement are regenerated by the simulation. Ticks, not clock timestamps, make
it exact.

**The game in progress is the same document**, still being written. Resuming = re-simulating
its log to the tick it was saved at, then handing the session back to live play, which keeps
appending to the same log. When the game ends, that document simply becomes a Recent replay.
One format, one store, one codec and one set of tests; the save can never disagree with the
replay.

- **Forward** (play, preset speeds, skip ahead, next wave, next action): keep stepping the
  session, silently (no rendering) when skipping.
- **Backward** (rewind, previous wave, undo an action, restart, scrubbing left): build a fresh
  session from the replay's config and data and re-simulate silently from tick 0 to the target.
- **Resume**: a backward seek to the saved tick, followed by live play.

Measured on this Mac (`classic-easy-blue-20` scenario, 25 134 ticks ≈ 7 min of play at 1×):
the whole game re-simulates headless in **~40 ms** (warm; ~80 ms cold). Its action log is
**2.9 KB**. That world is light (≤ 10 creeps, ≤ 3 projectiles); §10 sets the budgets that
decide whether anything faster is ever needed.

### Trade-offs of using the log for resume

| | Log re-simulation (chosen) | Saving a full state snapshot (fallback) |
|---|---|---|
| Code | Nothing beyond the replay system | Full state capture/restore for every entity, kept complete as Phases 2–4 add state |
| Exactness | Exact while `simVersion` matches (§4) | Exact always |
| Resume time | Grows with game length: ~40 ms for 20 waves today | Instant |
| After an app update that changes rules | Re-simulates under the new rules; the position may differ (§7.5) | Restores the exact position, then continues under new rules; needs a state migration whenever the state shape changes |
| Storage | ~20–40 KB per hour | One snapshot (~3–70 KB) on top of the log; only one game in progress, so size is not an issue |

The fallback is only built if the resume budget (§10) fails. It is the same state
capture/restore work as the in-memory keyframes in §5.6, so one piece of work would serve
both.

### Rejected alternatives

- **Per-action inverse undo** ("undo build = remove turret, refund"). The world keeps moving
  between actions: by the time a build is undone, the turret has killed creeps, earned bounty
  and consumed RNG draws. Reversing the action does not reverse its consequences, and every
  turret, combo and super turret in Phases 2–4 would need its own hand-written inverse.
- **Persisted keyframes** (full state copies saved with every replay). They hold no
  information the log does not, and they are large (measured with today's state fields, §9):
  a busy late game is ~68 KB per keyframe, so one every 10 s is ~25 MB per hour of play
  before compression, ~1 000× the action log. If rewinding long games turns out slow,
  keyframes are added **in memory only** (§5.6).

## 3. Concepts

| Term | Meaning |
|---|---|
| **Action** | One recorded command: `{tick, command, outcome, source?}`. `outcome` is `applied` or the `CommandRejected` reason; rejected commands are kept because replaying them is still exact and harmless. `source` is `lifecycle` for auto-pauses, so the timeline can label them. |
| **Replay** | Persisted document: config, version tags, data reference, mod delta, action log, wave markers, end tick, result, checkpoints. |
| **Game in progress** | The single replay document whose game has not ended (`status: active`). |
| **Timeline** | Ticks `0 … endTick`, with wave markers (from `WaveStarted`), action markers, and paused spans (ticks where the game clock was frozen). |
| **Checkpoint** | `{tick, stateHash}` every 600 ticks, stored in the replay, used to detect desyncs. |
| **Playback rate** | How fast the viewer watches (ticks per real second = `tickHz × rate`). Independent of the *recorded* game speed, which is itself an action (`SetSpeed`) and replays as recorded. |
| **Data blob** | The exact game-data documents a replay was played with, stored once per data signature and shared by every replay that used them. |

## 4. Versioning: what makes an old replay or save still play

A replay is re-simulated with code from the version of the app that opens it, so it needs
protection against two kinds of change:

1. **Data changes** (balance numbers, recipes, maps, mods). Fixed by embedding the data: each
   replay references a data blob holding the base `assets/data` documents it was played with
   (the whole set is 122 KB, 16 KB gzipped), plus its own `ModDelta`. Playback and resume
   build `GameData` from those, never from the current assets, so a resumed game also
   finishes with the numbers it started with. Blobs are deduplicated by signature, so every
   replay recorded on one app version shares a single blob.
2. **Rule code changes** (how the simulation behaves). Handled by a version tag:
   - `simVersion`: an integer in `onslaught_core`, bumped by any change that alters simulation
     behaviour. The fixture policy already requires such a change to update the regression
     fixtures in the same PR; that PR also bumps `simVersion` (a test pins the fixture hashes
     to the version, so forgetting the bump fails CI).
   - `appVersion` (from the app's pubspec, display only) and `dataSchemaVersion`.
   - Same `simVersion` ⇒ exact. Different `simVersion` ⇒ replays show a banner and checkpoints
     mark the first tick where they diverge; the game in progress asks first (§7.5). A data
     blob whose schema is older than the loader can migrate ⇒ the replay cannot be played (it
     stays listed so the player can delete it), and a game in progress can only be abandoned.

## 5. Core work (`packages/onslaught_core`, pure Dart)

New folder `lib/src/replay/`, exported from `onslaught_core.dart`.

### 5.1 Action log (recording)

- `GameSession` keeps an `ActionLog`: in `_apply`, append `{tick: stepIndex, command,
  outcome}` (outcome from whether the step emitted `CommandRejected` for it). `enqueue`
  takes an optional `source` that is copied onto the entry.
  Recording at *apply* time, not enqueue time, is what makes it exact: live input arrives
  between frames and is applied at the start of the next step.
- Wave markers from `WaveStarted`; paused spans from `PausedChanged`; checkpoints every 600
  ticks from `stateHash()`.
- A session can be created with an existing log (resume) and keeps appending to it.
- Always on (a list append per tap). `snapshot()` and `stateHash()` are unchanged, so **no
  regression fixture changes** (R15).

### 5.2 Replay document

```json
{
  "schemaVersion": 1,
  "kind": "replay",
  "id": "r_7f3a…",
  "status": "finished",
  "simVersion": 1,
  "dataSchemaVersion": 1,
  "dataSignature": 2873450123,
  "mod": null,
  "config": { "map": "map1", "mode": "normal", "difficulty": "easy",
              "profile": "classicFixed", "seed": 42 },
  "endTick": 25134,
  "result": { "outcome": "gameOver", "wave": 20, "kills": 200, "shots": 3100,
              "spent": 512.0, "score": 102400.0 },
  "waves": [ { "wave": 1, "tick": 0 }, { "wave": 2, "tick": 1212 } ],
  "pausedSpans": [ { "from": 4000, "to": 4600 } ],
  "actions": [ { "tick": 0, "command": { "type": "build", "turret": "blue",
                 "x": 534.0, "y": 300.0 }, "outcome": "applied" } ],
  "checkpoints": [ { "tick": 600, "hash": 123456789 } ]
}
```

- `status`: `active` (the game in progress), `finished`.
- `result.outcome`: `gameOver`, `challengePassed` / `challengeFailed` (Phase 5), or
  `abandoned`. Absent while active.
- `endTick`: for an active game, the tick it was last saved at (the resume target).
- `Replay.fromSession(...)`, `Replay.fromJson/toJson`, a `Migrator` from day one (R9).
- `dataSignature` = `fnv1a32(canonicalJson(base data documents))`; the mod delta is embedded
  in the replay (it is small and per game).
- Wall-clock fields (`startedAt`, `savedAt`) and `appVersion` live in the app's index entry,
  not here; the core has no wall clock (tenet 3).
- `Replay.toScenario()`: any player replay can become a regression fixture or a bug repro via
  `tool/fixture.dart`.

### 5.3 `ReplayPlayer`

Pure-Dart controller that owns a session and feeds it the log.

```dart
class ReplayPlayer {
  ReplayPlayer(GameData data, Replay replay, {ReplayTuning tuning});
  GameSession get session;      // the world at the cursor (read-only for views)
  int get tick; int get endTick; int get wave;
  bool get playing; double get rate;
  void play(); void pause(); void restart();
  void setRate(double preset);  // one of tuning.rates: 0.5, 1, 2, 4, 8
  void advance(double realSeconds);  // per frame: steps tickHz × rate × dt
  void seekToTick(int t);       // the one seek primitive (§5.6)
  void seekToWave(int n);       // start of wave n, past or future, within the recording
  void skip(Duration d);        // ±10 s buttons
  void stepAction(int delta);   // previous / next action (undo / redo)
  Stream<ReplayEvent> get events; // GameEvents during normal play, plus Seeked, Desync, Ended
}
```

- Seeks are silent: no `GameEvent`s reach the presentation; one `Seeked` signal is emitted so
  views reset.
- Paused stretches in the recording are skipped by default (the sim ticks while paused, so a
  long pause, including every auto-pause, would otherwise be dead air).
- Crossing a checkpoint compares `stateHash()`; a mismatch emits `Desync(tick)`.
- Playback stops at `endTick`; "next wave" past the last recorded wave jumps to the end.
- `ReplayTuning` (rates, ±skip size, checkpoint spacing) is playback tuning, not balance; it
  lives in `replay/` with defaults the app can override, outside `rules/` and `sim/` (R7).

### 5.4 `GameResumer`

`GameResumer.resume(data, replay)` builds the session, re-simulates the log to `endTick` in
chunks (so the app can show progress and stay responsive), checks every checkpoint it
crosses, and returns the live session with its log attached, or a `ResumeProblem`
(`versionMismatch`, `desync(tick)`, `dataUnreadable`). Pure Dart, shares the re-simulation
loop with `ReplayPlayer.seekToTick`.

### 5.5 "Take over from here" (optional, §11 R10)

From a paused replay at tick `T`, start a new game in progress from the replay session with
its action log truncated at `T`: the real "undo a mistake and play on" feature. It obeys the
one-game rule (§7.6). It is a new feature, not a rule change, so it sits behind a flag and
never touches the classic flow.

### 5.6 Seek hook and in-memory keyframes (deferred)

`seekToTick` is the only place that decides how to reach a tick. Version 1: forward ⇒ keep
stepping; backward ⇒ new session, re-simulate from 0. If a budget in §10 is exceeded, add
full session state capture/restore (with a restore-equivalence test over every scenario
fixture) and an in-memory `KeyframeStore` behind the same function (state at each wave start,
captured during playback, never persisted). The store is held to a **byte budget** and is
**trimmed when the OS reports memory pressure** (§6.3). Keyframes are a pure cache, so
dropping any or all of them never loses data; the next backward seek just re-simulates
further. The same capture/restore would then also put one snapshot in the game-in-progress
save (§2 fallback). The replay format and the UI do not change either way.

`KeyframeStore` API (pure Dart; the core knows nothing about the OS signals, which the app
maps onto these calls):

```dart
class KeyframeStore {
  KeyframeStore({required int budgetBytes});
  int get count; int get approxBytes; int get budgetBytes;
  void add(int tick, SessionState state);  // evicts to stay within budgetBytes
  SessionState? atOrBefore(int tick);
  void trim({int? keepNearestTo});  // drop everything, except optionally the keyframe
                                    // at or before that tick
  void reduceBudget();              // halve budgetBytes (floor: one keyframe) after pressure
}
```

- `approxBytes` comes from each state's entity counts × a per-entity cost (the measured
  ~170 B per creep, ~185 B per turret, ~130 B per projectile in JSON form, rounded up for
  Dart object overhead), so the budget is enforced without walking the object graph.
- Eviction order under the budget: periodic keyframes farthest from the cursor first; wave-start
  keyframes last.
- The default budget (proposed 16 MB on phones, 64 MB on desktop) is `ReplayTuning`, not
  balance (R7).

### 6.3 Memory pressure: trimming in-memory caches

Only matters once in-memory keyframes exist (R8, and the reverse-play ring in R9). Without
them, a replay holds a few KB of log and one `GameData`, and there is nothing worth trimming.

**What the OS tells a Flutter app** (checked in the pinned SDK's engine source and Android's
memory guide):

| Platform | OS signal | Reaches Dart as | Notes |
|---|---|---|---|
| Android 14+ (API 34+) | `onTrimMemory(TRIM_MEMORY_UI_HIDDEN = 20)` when the UI leaves the screen; `onTrimMemory(TRIM_MEMORY_BACKGROUND = 40)` when the process becomes a kill candidate | `WidgetsBindingObserver.didHaveMemoryPressure()` (the `memoryPressure` message on `SystemChannels.system`) | Android 14 stopped delivering the other ("running") levels and Android 15 deprecated them, so **there is no foreground memory signal on Android 14+**. |
| Android ≤ 13 | Also `TRIM_MEMORY_RUNNING_LOW = 10` / `RUNNING_CRITICAL = 15` while in the foreground | Same | `RUNNING_MODERATE = 5` is dropped by Flutter. |
| iOS | `UIApplicationDidReceiveMemoryWarningNotification` (foreground or background) | Same | The engine also sends one when the Flutter view controller disappears; plain backgrounding does **not** send one. |
| macOS, Windows, Linux, web | — | Not relied on | Budget cap only. |

Engine details (`FlutterActivityAndFragmentDelegate.onTrimMemory`): Flutter forwards a level
only when `level >= TRIM_MEMORY_RUNNING_LOW` and the first frame has rendered, and **drops the
level number**: Dart cannot tell `UI_HIDDEN` from `BACKGROUND`. The policy below does not need
the level, so **no Android or iOS native code is needed**. If a level-specific policy is ever
wanted, override `onTrimMemory` in `MainActivity.kt` and forward the level over a
`MethodChannel`; that is not planned.

`PaintingBinding` already clears Flutter's `imageCache` on the same signal. Flame's own
`Images` cache (the atlases being drawn) is not ours to trim here.

**Policy** (`MemoryTrimmer` in `lib/services/`, one `WidgetsBindingObserver` plus the
lifecycle listener from §7.2, calling every registered `Trimmable`):

| Trigger | Action |
|---|---|
| App `hidden` / `paused` (lifecycle), on every platform | `KeyframeStore.trim()`: drop **all** keyframes and the reverse-play ring. The game in progress is already saved (§7.3), and keyframes are not needed to save. Being smaller while backgrounded also makes Android's low-memory killer less likely to pick this process. |
| `didHaveMemoryPressure` while hidden (Android `UI_HIDDEN` / `BACKGROUND`) | Same as above (idempotent; the signal and the lifecycle change can arrive in either order). |
| `didHaveMemoryPressure` while in the foreground (iOS memory warning; Android ≤ 13 running levels) | `trim(keepNearestTo: cursor)` so the next short rewind stays fast; `reduceBudget()` for the rest of this replay so the store does not refill into the same pressure; stop building the reverse-play ring until the replay is reopened. |
| Back to `resumed` | Nothing eager. Keyframes rebuild lazily as playback passes wave starts, within the (possibly reduced) budget. |
| Replay screen closed | Drop the store entirely. |

Other caches registered as `Trimmable`: parsed replay documents and `GameData` built from
data blobs (keep only the one in use).

**Tests and QA**

## 7. Resume: pause window, auto-pause, save and continue

Today there is no pause window and no lifecycle handling: pause is only the top-bar button
(`hud/top_bar.dart`), the top bar's exit button goes straight to `/` and drops the game
(`game_screen.dart`, `onExit`), and `/game/:mapId` always starts a fresh game.

The original had no pause window either: its pause control is a toggle with a blinking icon
(`GamePause.as`, `GameManager.pauseToggle/pauseOn/pauseOff`, which play the "Pause" /
"UnPause" sounds), and it has no focus-loss handling. Its Settings window did pause the game
(reference §"Settings window"). The pause *rule* (every world command refused while paused)
is unchanged; the window and auto-pause are presentation and platform behaviour, proposed as a
`docs/DEVIATIONS.md` row (§12).

### 7.1 Pause window

A modal card over the dimmed board, built against `GameViewModel` (widget + golden tests):

- Title "Paused"; one line of context (map, difficulty, wave, lives, cash).
- **Resume** (primary): closes the window and sends `SetPaused(false)`; plays "UnPause".
- **View board**: closes the window but keeps the game paused, with a "Paused, tap to resume"
  chip using the original's blinking pause icon, so the player can inspect turrets
  (inspection works while paused; world commands are refused, as in the original).
- **Restart**: confirmation ("Abandon this game and start again?"), then §7.6 restart.
- **Main menu**: leaves with the game kept in progress ("You can continue from the main
  menu"). No confirmation needed, since nothing is lost.
- Later: **Settings** (Phase 5), like the original's settings window, which also pauses.

Opened by: the top-bar pause button, the top-bar exit button (which no longer drops the
game), Android back, `Esc` on desktop/web, and every return from an auto-pause. `P` keeps the
original's plain pause toggle without the window (open decision §12).

### 7.2 Auto-pause

`GameScreen` registers an `AppLifecycleListener` while a live game is shown:

| Lifecycle change | Platforms | Action |
|---|---|---|
| `inactive` | iOS/Android (incoming call, control centre, app switcher, permission dialog) | auto-pause |
| `inactive` | desktop (window loses focus), web (tab loses focus) | auto-pause if the "Pause when the window loses focus" setting is on (default on) |
| `hidden` / `paused` | all (app backgrounded, tab hidden, window minimised) | auto-pause + save (§7.3) |
| `detached` | all | save (best effort) |
| `resumed` | all | if auto-paused, show the pause window; never auto-unpause |

Auto-pause must take effect **immediately**, because once the app is hidden Flutter stops
producing frames and no simulation step would run to apply a queued command. So the view model
enqueues `SetPaused(true)` with `source: lifecycle` and immediately runs one step itself (in
`GameSession.step`, commands apply before the clock ticks, so the step freezes the game with
zero game time passing). The pause is then in the log, the world is frozen, and the save
written next has the exact paused state. Already paused ⇒ nothing is sent.

No "Pause" sound on auto-pause (the player has left); audio is suspended with the app.

### 7.3 Saving the game in progress

The game in progress is a replay document with `status: active`, written through
`ReplayStore` (§8):

- **Created** when the game starts (status `active`, empty log).
- **Rewritten** after every applied action, at every wave start, every 5 s of play (a
  heartbeat that only advances `endTick`), and on every auto-pause / `hidden` / `detached`.
  Each write is the log (~20–40 KB per hour, estimate), so this is cheap. Writes are queued
  and coalesced so a slow write never stacks up.
- **Worst case** (process killed with no lifecycle callback, e.g. a crash or an OS kill
  without warning): no player action is lost; the game resumes at most ~5 s of play earlier.
  On iOS and Android, swiping the app away from the switcher happens after `hidden` /
  `paused`, so the normal path has already saved the exact paused state. On web, IndexedDB
  writes may not finish while a tab closes; the heartbeat bounds the loss.

### 7.4 Continue

- On launch, `ReplayStore` reconciles (§8) and reports the game in progress, if any.
- The home screen shows a **Continue** card (map, mode, difficulty, wave, lives, cash,
  "last played …") above the new-game buttons, with **Abandon** as a secondary action.
- Continue ⇒ route `/game/continue` ⇒ load the document and its data blob ⇒ `GameResumer`
  re-simulates to `endTick` (a "Resuming…" progress view if it takes longer than ~200 ms) ⇒
  the game opens **paused, with the pause window showing**, so the player gets their
  bearings before anything moves. If the save came from a heartbeat (not paused), the resumed
  session applies a `SetPaused(true)` (`source: lifecycle`) on its first step, so it still
  opens paused.
- The live session keeps appending to the same document and id; the replay of a resumed game
  is one continuous timeline, with the auto-pause visible as an action.

### 7.5 Version changes and failures

| `GameResumer` result | What the player sees |
|---|---|
| OK | The game, paused, exactly where they left it |
| `versionMismatch` (`simVersion` differs; the app updated with rule changes) | "This game was saved on an earlier version. It will be replayed with the new rules, so things may turn out slightly differently." **Resume anyway** / **Abandon** |
| `desync(tick)` during re-simulation (should not happen with a matching version; would indicate a determinism bug) | Same dialog, and the problem is logged for QA |
| `dataUnreadable` (data schema too old to migrate) | "This game can't be continued on this version." **Abandon** only |

`simVersion` bumps should be rare after v1 ships (v1 behaviour is frozen by the fixtures), so
this path is an edge case, not the normal flow.

### 7.6 One game in progress

- `ReplayStore` holds at most one `active` document; `startGame` throws if one exists. The UI
  never reaches that, because:
- **Every way to start a game** (Play Classic, the map picker, Phase 5 mode/map/challenge/
  sandbox/tutorial flows, restart, "take over from here") goes through one `GameLauncher`
  service in `lib/app/`. With a game in progress it refuses and the caller shows the
  **game in progress** sheet: "You have a game in progress on Classic, wave 12."
  **Continue** / **Abandon and start new** (with confirmation).
- go_router `redirect` is the backstop: any `/game/new…` while a game is in progress redirects
  to `/` with that sheet open. Routes: `/game/new?map=&mode=&difficulty=` and
  `/game/continue` replace `/game/:mapId`.
- **Abandon**: confirmation ("Abandon this game? You'll still be able to watch it in Recent
  replays."), then status `finished`, `result.outcome: abandoned`, moved to Recent.
- **Game over** (and challenge over): the game in progress ends automatically and moves to
  Recent; the game-over panel's **Restart** starts a new game straight away (nothing to
  abandon) and **Main menu** goes home.
- **Restart** from the pause window = abandon + start a new game with the same map, mode and
  difficulty and a new seed.
- Not games in progress: the Phase 5 attract demo behind the main menu, and replay playback.
- Open decision (§12): whether the tutorial counts as a game in progress.

## 8. Storage: `ReplayStore`

A separate **lazy** Hive box, `replays`. The existing `HiveDocumentStore` uses
`Hive.openBox` (`document_store.dart:42`), which loads every value into memory at startup;
a lazy box (`Hive.openLazyBox`) reads values only when asked, so stored replays cost no memory
until one is opened. `ReplayStore` sits on a `DocumentStore` (a lazy Hive implementation for
the app, `MemoryDocumentStore` in tests) with three key families:

| Key | Holds | Size |
|---|---|---|
| `index` | `{schemaVersion, active: entry?, recent: [entry…], saved: [entry…]}`. Entry = `id, map, mode, difficulty, wave, lives, cash, kills, score, outcome, endTick, startedAt, savedAt, appVersion, simVersion, dataSignature` (+ `name` for saved replays). | ~200 B per entry |
| `replay/<id>` | The replay document (§5.2). | ~20–40 KB per hour of play (estimate) |
| `data/<signature>` | A data blob: the base data documents, shared by all replays with that signature. | ~122 KB, once per app version that recorded something |

Rules:

- **Game in progress**: `index.active`, at most one (§7.6). It is not in Recent and does not
  count toward the Recent limit. When it ends (game over, abandon) it moves to the top of
  Recent.
- **Recent**: finished games, newest first, at most `recentLimit` (default 10). Adding the
  11th deletes the oldest Recent replay. Optional age cleanup: `recentMaxAgeDays` (default
  off; 30 if the owner wants it) runs at app start. It never touches the game in progress or
  Saved.
- **Saved**: **Save** moves an entry from Recent to Saved (the document is not copied) with an
  optional name. **Unsave** moves it back to the top of Recent (which may push out the
  oldest). Saved replays are never cleaned up automatically. **Delete** removes the entry and
  its document.
- **Blob cleanup**: after any delete, remove data blobs no remaining entry references
  (including the game in progress).
- **Crash safety**: write the replay document and blob first, the index last. At app start,
  reconcile: delete `replay/*` documents no entry points to, drop entries whose document is
  missing, keep at most one `active` (if a crash ever left two, the newer stays active and
  the older becomes an abandoned Recent replay), then run blob cleanup.
- Index, replay documents and blobs are all schema-versioned with migrators (R9).
- Settings (`recentLimit`, `recentMaxAgeDays`, `pauseOnFocusLoss`) live in `Settings`.

## 9. Storage budget

Measured with today's simulation (Phase 1 state fields); late-game rows are estimates.

| | Per hour of play | 10 Recent one-hour games |
|---|---|---|
| Action log (~70 B per action, ~300–600 actions per active hour, estimate) | ~20–40 KB | < 0.5 MB |
| Checkpoints (360 per hour × ~25 B) | ~9 KB | ~0.1 MB |
| Data blob (shared) | — | ~122 KB per app version |
| Game in progress | one more replay document | — |
| *Rejected:* keyframes every 10 s, light board (~3 KB each, measured) | ~1.1 MB | ~11 MB |
| *Rejected:* keyframes every 10 s, busy late game (~68 KB each, measured with today's fields; more once Phases 2–4 add state) | ~25 MB+ | ~250 MB+ |

Storage is not what limits the Recent list; the limit of 10 and the optional 30-day cleanup
are UX choices.
